# Code Atlas 0.3：以任务和改动为中心的代码审阅

记录日期：2026-11-26。

## 为什么调整方向

前两版把项目结构、依赖关系和源码放在一起，解决了“在哪里”的一部分问题，却仍要求使用者先理解大量节点与连线。对 AI 一次生成许多文件的情况，把全部依赖展示出来并不会自动降低阅读成本。

本版将主入口改为代码审阅工作台：先确定这次要核对的问题，再选择相关源码，最后阅读带引用的报告。文件导航用于选择范围，关系图用于回答局部结构问题，二者都不再占据默认首屏。

这个方向符合课程第三部分的开放要求：参考已有插件，结合使用智能体的经验增强 DSH。该部分没有要求必须以代码树或依赖图为主界面，见 [任务原文](../phase_cli_2.md)第三部分。

## 本次已实现

### 视图与信息层次

- 使用暖白、暖灰、陶土橙和较轻的分隔线，提供浅色、深色切换；样式限定在插件页面内。
- 任务输入放在页面底部，保留当前范围、生成状态和停止生成操作。
- 默认收起文件导航。需要定位符号时再打开“文件”，需要核对正文时再打开源码。
- 主页面分为“工作台”“阅读报告”“关系参考”。工作台优先呈现任务选择与快照变化，完整关系图保留在辅助页面。
- 报告继续保留源码引用、核验问题、范围提示及 Markdown 导出；源码阅读、返回导航与 SVG 导出继续使用原有能力。

这是对 Claude Code 简洁、文字优先界面的风格借鉴，所用颜色和排版是本项目的设计选择，不是官方色值规范，也不表示与 Claude 有产品关系。Claude Desktop 的官方文档更值得借鉴的是围绕任务、变更和按需面板组织工作，而不只是某一套颜色。[Claude Desktop 官方文档](https://code.claude.com/docs/en/desktop#review-changes-with-diff-view)

### 四类审阅意图

| 意图 | 本版组织的分析内容 | 能力边界 |
|---|---|---|
| `flow`：运行流程 | 从具体入口解释输入、关键处理、分支、状态变化、错误恢复与结果 | 静态调用与模型解释不能证明实际执行顺序，也不是完整运行追踪 |
| `design`：设计取舍 | 先指出职责、变化点及源码依据，再比较接口、对象组合、模式与较简单方案 | 是设计建议；不把依赖多、类大或有条件分支直接判为设计错误 |
| `refactor`：重构计划 | 明确应保持的行为，拆成修改范围、验证方法和回退方式可说明的小步骤 | 只产生计划，不自动修改项目源码，不声称已经完成重构或运行测试 |
| `change-review`：快照变化核验 | 优先查看最近两次成功扫描间的新增、修改、删除路径，讨论当前代码的影响与核验重点 | 文件哈希比较，不是 Git diff；没有旧正文或逐行补丁 |

四类意图共用有范围限制的源码上下文、报告结构和引用校验。服务端检查意图枚举，并为不同意图提供相应要求；没有为了增加入口而建立四套重复的分析器或渲染器。

设计模式建议须说明实际问题、拟定接口、对象如何组合、收益和新增复杂性，同时比较“不引入模式”的方案。没有证据支持时，应保留现状。重构计划须说明不变量和验证步骤；报告里的核验问题仍是建议，不等于已经通过的检查。

实现入口见 [任务界面](../extensions/dsh-code-atlas/src/client/AtlasPage.tsx)、[工作台](../extensions/dsh-code-atlas/src/client/NewWorkbench.tsx) 与 [模型适配器](../extensions/dsh-code-atlas/src/host/DshGuideProvider.ts)。

### 快照变化到底比较什么

本版比较同一会话、同一工作区中相邻两次成功扫描收录的文件路径与内容哈希，包括已收录的源码和配置。当前保存的比较结果只描述路径的新增、修改、删除；它不保存一套可浏览的历史版本，也不保存上一版正文。

| 情况 | 本版行为 |
|---|---|
| 第一次扫描 | 建立起点，明确显示尚无比较基线；不能据此判断之前有没有修改 |
| 修改代码后再次成功扫描 | 对比前一次成功扫描，显示新增、修改、删除路径 |
| 扫描失败或取消 | 不发布部分结果，不把失败扫描作为新基线 |
| 切换工作区 | 不沿用另一个工作区的比较基线 |
| 文件已删除 | 展示路径与删除状态，旧位置不能点击跳转，不编造已删除正文 |
| 文件没有可定位的代码节点 | 提示材料缺口，不能给它伪造源码引用 |
| 再次扫描但内容相同 | 最新一对成功扫描没有变化，不继续把更早的变化当作“本次变化” |

因此，使用流程应是：先扫描留下起点，完成一轮改动，再扫描并核验。若改动在首次扫描之前已经发生，本功能无法还原改动前的状态。它也不能区分代码由人还是 AI 编写，不能代替提交记录、暂存区或分支比较。

变化核验优先收集仍存在的变化文件中的当前代码；删除文件只有路径元数据。变化文件可能仅提供部分当前符号，列为修改不代表变化部位均已读取；例如同文件顶层常量的修改可能未进入所选函数正文。没有函数或类的源码文件可提供受预算限制的文件片段。生成与发布时继续核验快照、比较基线和源码版本，避免把旧比较结果发布到新一轮扫描中。实现见 [AtlasWorkbench](../extensions/dsh-code-atlas/src/core/AtlasWorkbench.ts)。

## 哪些功能更值得继续做

我的判断是：对大型工程，最值得优先投入的是“围绕一次任务或一次改动减少人需要核对的内容”。设计模式建议和重构计划能够帮助做决定，但不能替代变更证据与验证结果。

| 优先级 | 方向 | 解决的问题 | 本次状态 |
|---|---|---|---|
| 优先完善 | 任务流程与快照变化核验 | 从明确入口或变化文件开始，缩小阅读范围，暴露材料缺口 | 已有四类意图及快照路径比较；仍受上下文范围限制 |
| 下一步重点 | 真正的 Git 差异审阅 | 直接核对改了哪些行、相对哪个版本变化、删除了什么 | 尚未实现 |
| 下一步重点 | 测试与执行证据 | 把“建议验证”变成有版本、有命令、有结果的证据 | 尚未接入被分析项目的测试执行或结果归集 |
| 证据具备后再做 | 人审补丁与小步重构 | 将建议变成可审阅、可验证、可回退的修改 | 当前只提供计划，不自动应用补丁 |
| 辅助保留 | 局部关系、模式参考与结构导航 | 在需要时定位接口、调用目标和协作对象 | 关系参考与原扩展点保留，不扩大全量图的主导地位 |

### 真正的 Git 差异审阅

应让使用者明确选择基线，例如工作区相对 `HEAD`、暂存区相对 `HEAD`、某个提交或明确的分支基线，并单独处理未跟踪文件。报告应关联实际补丁中的文件、行与基线标识；当工作区再次变化时，旧审阅结果要能识别为过期。

这样模型才能依据真实的前后代码，说明行为变化、删除实现和调用方影响。Git 信息应通过独立边界适配为审阅数据，不让页面或语言分析器各自理解 Git 输出。不能把现在的快照列表改一个名称，就宣称完成了这项功能。

### 测试与执行证据

优先关联已有 CI 或已保存的运行结果。证据至少应保留命令、工作目录、源码版本或哈希、结束状态、退出码与结果摘要；某次检查通过，只对当时的代码与检查范围负责。

模型提出的测试建议、使用者的“已核对”标记，以及实际执行结果应明确区分。将来若增加运行测试的能力，需要独立的执行边界与取消、超时、输出限制，不能让报告正文直接成为可执行命令。Claude 的官方实践也强调给智能体明确的检查，并区分模型决定与系统实际保证的行为。[Claude Code 官方最佳实践](https://code.claude.com/docs/en/best-practices)

### 人审补丁与重构

推荐的后续闭环是：选定基线与任务 → 说明行为不变量 → 生成小范围候选补丁 → 人逐项审阅 → 核验源码仍与基线一致 → 应用并运行相关检查 → 展示结果与回退办法。

在这个闭环具备前，继续提供重构计划更合适。特别是设计模式重构，应先问真实的变化点在哪里、哪个模块隐藏哪些知识，再比较保持现状、小范围抽取与引入模式的代价。不能把一个方法拆成许多类，就当作设计已经改善。只读探索与规划本身也是成熟工具中的独立工作阶段。[Continue Plan Mode 官方说明](https://docs.continue.dev/ide-extensions/agent/plan-mode)

## 与课件原则和已有模式的关系

本次调整依据课程材料《A Philosophy of Software Design》、四种模式课件及此前整理的《课程设计原则与模式阅读笔记》中的原则：

| 课程关注点 | 本版的设计选择 |
|---|---|
| 降低整体复杂性与认知负荷 | 首屏围绕一次任务，文件和关系按需展开，不要求先理解整个工程 |
| 信息隐藏与深模块 | 编译器对象、DSH 文件访问、远程结果封装、模型流协议仍由各边界模块处理 |
| 接口通用，功能满足当前需求 | 多种报告共用上下文与引用校验，没有建立万能自动重构系统 |
| 不同层提供不同抽象 | 语言层提供源码事实，工作台组织范围与状态，模型提供解释，页面负责阅读交互 |
| 避免过度设计与无价值的直通层 | 按真实变化点划模块，不为每个菜单项机械增加一套类层次 |
| 设计判断须有取舍 | 模式建议同时讨论较简单方案与新增成本；不能靠模式数量证明低耦合 |

原有四种课程设计模式的职责继续保留：

- **Adapter**：TS7 源码事实转换、DSH 文件访问、远程结果与模型流协议的适配各有归属。
- **Strategy**：依赖与使用者两种阅读算法继续由 `ReadingStrategy` 提供。新的审阅意图负责报告目的，不混入关系遍历算法。
- **Decorator**：公开 API、已读和测试文件标签继续通过相同接口包装、委托和组合，不把这些提示写进 SVG 图形或源码事实。
- **Observer**：工作台实例发布状态，原生订阅与客户端面板同步；会话关闭、注销及卸载仍有对应释放流程。

统一源码模型与 `LanguageProvider` 保留，TS/JS 分析继续封装在 TypeScript 适配器内。关系图继续复用已有的 box、line、`SvgDocument` 和 `SvgCodec`；它从主入口退到辅助页面，不意味着抛弃 Phase 1/2 的图形能力或绕过扩展点。

## 验证范围与当前限制

本轮模型功能使用无网络测试替身检查，未额外调用付费模型。此前版本的一次在线模型结果属于其自身记录，不能作为本版四种审阅意图都已经在线验收的证明。

本版的具体测试结果、安装检查、截图与桌面操作范围统一见 [验收记录](code-atlas-verification.md)。本文不填写尚未确认的测试数量，也不把旧版截图作为本次视图重构的效果。

当前仍是有界、只读的代码理解与建议工具：不提供完整运行控制流，不对整个工程作正确性保证；不读取真实 Git diff，不执行被分析项目的测试，不自动修改或重构源码。快照变化、模型报告和手动核验标记均不能替代这些能力。
